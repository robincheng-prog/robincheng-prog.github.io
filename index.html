Windows 11 設定為 HMI

將 Windows 11 設定為工業或專用人機介面（HMI）時，核心目標是確保開機直接進入圖控軟體、關閉干擾通知、防止睡眠與防止操作員亂按系統。

✅ 1. 電源與睡眠設定（防止自動關機或休眠）

HMI 需要 24 小時不間斷運行，絕不能進入省電模式。

  • 進入 設定 > 系統 > 電源與電池。

  • 將「螢幕關閉時間」與「電腦進入睡眠狀態的時間」皆設為 「從不」 (Never)。

  • 檢查控制台的傳統電源選項，確保 PCI Express 或 USB 選擇性暫停功能被停用，避免通訊模組斷線。

✅ 2. 略過登入與自動開機登入（AutoLogon）

開機後必須自動進入桌面並啟動 HMI 軟體，不能卡在密碼輸入畫面。

  • 按下 Win + R 鍵，輸入 netplwiz 並按 Enter。

  • 在跳出的視窗中，取消勾選「必須輸入使用者名稱和密碼，才能使用這台電腦」。

  • 點擊「確定」後，系統會要求你輸入一次目前的帳號與密碼以完成綁定。

✅ 3. 設定 HMI 軟體開機自動執行

讓圖控軟體（如 InTouch、WinCC、KingView 或自寫 SCADA）隨 Windows 啟動。

  • 將你的 HMI 執行檔捷徑，放入 Windows 的啟動資料夾中：

    1. 按下 Win + R，輸入 shell:startup 並按 Enter。

    2. 將 HMI 的捷徑貼到此資料夾中。

✅ 4. 關閉系統更新與干擾通知

避免 HMI 運作中途跳出 Windows 更新重開機或右下角彈出通知。

  • 關閉通知：進入 設定 > 系統 > 通知，將通知總開關設為 關閉，或開啟「專注模式」。

  • 暫緩 Windows 更新：

  • 進入 設定 > Windows 更新，選擇「暫停更新」拉到最長時間（家用/專業版極限）。

  • 若為企業長期穩定需求，建議直接評估使用 Windows 11 IoT Enterprise LTSC 版本並透過群組原則徹底關閉自動更新。

✅ 5. 隱藏介面與防止誤觸（Kiosk 模式或調整工作列）

如果希望操作員只能操作 HMI 畫面，不能點擊桌面或開啟瀏覽器：

  • 自動隱藏工作列：右鍵點選工作列選擇「工作列設定」>「工作列行為」，勾選「自動隱藏工作列」。

  • 鎖定快捷鍵與權限：透過 HMI 軟體自身的帳號權限（如 9 級權限或登入畫面）來管控操作員。如果是單一網頁或 UWP 應用程式，可進一步利用 Windows 11 的 指派存取權 (Assigned Access / Kiosk 模式) 建立單一應用程式鎖定帳戶。

Chrome 網頁型 HMI

由於 Windows 11 內建的「指派存取權 (Kiosk)」選單只強制綁定 Microsoft Edge，無法直接選取 Google Chrome 作為全螢幕 Kiosk 軟體。
既然你的 HMI 是網頁型且指定使用 Chrome，最佳的解決方案是利用 Chrome 內建的 Kiosk 模式（資訊看板模式），並搭配 Windows 的自動開機登入與自訂 Shell (殼層)。這樣操作員開機後，電腦只會跳出 Chrome 且完全隱藏 Windows 桌面與工作列，也無法按 F11 或 Alt+F4 退出。
以下是完整的設定步驟：

🛠️ 第一步：建立專用的 Windows 本地帳戶

為了系統安全與日後維護，請先建立一個獨立的 HMI 操作員帳戶。

  1. 進入 設定 > 帳戶 > 其他使用者。

  2. 點擊「新增帳戶」，選擇「我沒有這名人員的登入資訊」。

  3. 點擊「新增沒有 Microsoft 帳戶的使用者」，輸入名稱（例如：HMI_User），密碼可留空（方便自動登入）。

這是最關鍵的一步。我們要讓 HMI_User 這個帳戶登入時，不要載入 Windows 的傳統桌面 (explorer.exe)，而是直接載入我們的 Chrome 腳本。這樣操作員就完全摸不到工作列、開始功能表和桌面。

  1. 按下 Win + R，輸入 regedit 並按 Enter 開啟登錄編輯程式。

  2. 導覽至以下路徑：
    HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Windows NT\CurrentVersion\IniFileMapping\system.ini\boot

  4. 關閉登錄編輯程式，並切換登入到你剛剛建立的 HMI_User 帳戶。

  5. 在 HMI_User 帳戶下，按下 Win + R，輸入 regedit 開啟登錄編輯程式。

  6. 導覽至目前使用者的路徑：
    HKEY_CURRENT_USER\Software\Microsoft\Windows NT\CurrentVersion\Winlogon

  7. 在右側空白處點右鍵 > 新增 > 字串值，命名為 Shell。

  8. 連點兩下剛建立的 Shell，在「數值資料」填入剛才 .bat 檔的絕對路徑：C:\start_hmi.bat。

💡 設定完成後的維護與退出方法

  • 實際運行效果：以後重啟電腦，Windows 11 會自動登入 HMI_User，並且畫面上只會出現 Chrome 顯示的 HMI 網頁，沒有滑鼠右鍵選單，沒有工作列，按 Alt + F4 或 F11 都無效。

  • 工程師如何退出進行維護？

    1. 在 HMI 畫面上按下 Ctrl + Alt + Del。

    2. 選擇「登出」或「切換使用者」。

    3. 切換回你的系統管理員帳戶，即可正常使用 Windows 11 桌面進行軟體修改或 PLC 通訊設定。

作者： Ayden

一、 什麼是 SBOM？為什麼我們需要它？

SBOM（Software Bill of Materials） 是軟體的「成分標籤」，詳細記錄了專案中所使用的所有第三方套件、開源元件及版本號。

導入主因：

  1. 合規要求： 歐盟網路韌性法案 (CRA) 等國際法規強制要求產品出廠需具備 SBOM，並有對應的漏洞管理機制。
  2. 零日漏洞快速應變： 當爆發重大資安漏洞（如 Log4j 事件）時，透過掃描 SBOM，能在幾秒鐘內確認我們的產品是否受影響，無須重新編譯原始碼。

二、 團隊標準工作流程 (DevSecOps)

為了保持開發效率並兼顧資安，我們將採用「產出」與「掃描」分離的職責分工模式：

  • 開發團隊： 負責在編譯時，產出正確的 SBOM 檔案。
  • 資安/維運團隊： 拿著 SBOM 檔案進行漏洞比對。

  1. 將製作好的隨身碟插上那台要清除 SSD 的目標電腦。

  3. 畫面上會跳出一個小視窗（Boot Menu），用鍵盤上下鍵選擇你的 USB 隨身碟名稱，然後按 Enter。

步驟 5：進入全自動抹除流程

  1. 隨身碟開機成功後，會先看到 SystemRescue 的黑底白字 Grub 啟動選單。直接按 Enter（選擇第一項預設啟動，或放著不管它也會自動倒數進入）。
  2. 電腦會開始跑一堆 Linux 的開機偵測指令（大約需要 15~30 秒，視電腦效能而定）。
  3. 高潮來了： 系統一載入完畢，畫面的所有雜亂文字會被自動清空（Clear），然後立刻彈出你寫的純英文畫面：
  • 標題顯示：🔍 SYSTEMRESCUE AUTO-ERASE ACTIVATED
    • 下方會整齊列出這台電腦上偵測到的 NVMe SSD 裝置路徑、容量與型號。
    • 最下方顯示黃色警告：⚠️ WARNING: ALL DATA ON THE DRIVES ABOVE WILL BE PERMANENTLY ERASED!
  1. 仔細核對畫面上顯示的 SSD 型號是否就是你想清除的那顆。
  2. 確認無誤後，在鍵盤按下 Enter 鍵。
  3. 系統會呼叫內建的硬體指令，這時畫面會顯示 ⚡ Erasing device: /dev/nvme0n1 …。
  4. 大約只需 1~3 秒，畫面就會跳出綠色的 ✅ /dev/nvme0n1 successfully erased!。
  5. 抹除結束後，畫面會跳出 🎉 All tasks finished successfully. Press [Enter] to power off the system…。
  6. 最後再按一次 Enter 鍵，電腦就會自動關機，這時你就可以安全拔下隨身碟，這顆 SSD 的內容已經徹底灰飛煙滅，且完全不傷硬碟健康。

⚠️ 離線操作時的終極排錯（萬一遇到 Erase Failed）

在沒有網路的環境下，如果執行到一半畫面跳出紅色的 ❌ /dev/nvme0n1 erase failed!，這 100% 不是隨身碟壞掉，而是主機板 BIOS 的硬體保護機制造成的。
因為許多主機板為了防止病毒破壞硬碟，開機時會自動把 SSD 狀態鎖定在 “Frozen” (凍結) 狀態，不准任何人發出清除指令。
這時的解決三板斧（照順序嘗試）：

  1. 關閉 BIOS 鎖定：重啟電腦進入 BIOS 設定畫面（通常是按 Del 或 F2），尋找關鍵字如 Security Freeze Lock、SSD Secure Erase Support 或 Block Erase，將其設定為 Disabled (關閉)，存檔重開機即可。
  2. 拔插解鎖法（桌機適用）：當腳本卡在失敗、要求你按 Enter 關機前，直接打開電腦機殼，把那顆 NVMe SSD 的訊號線/電源線拔掉，數 3 秒後再插回去（此動作在 Linux 下會強制重設硬碟狀態並自動解鎖）。拔插好之後，直接在鍵盤按下 Ctrl + C 中斷腳本，然後輸入 bash /run/archiso/bootmnt/sysrescue.d/nvme_erase.sh 重新手動觸發一次即可成功！
  3. 改用 Crypto Erase (加密抹除)：有些新型 SSD 只吃加密抹除（一秒銷毀金鑰）。如果上面方法都失敗，你可以把隨身碟插回 Windows 電腦，用記事本打開 nvme_erase.sh，將裡面第 44 行的 –ses=1 改成 –ses=2，存檔後再去目標電腦跑一次，通常就能順利解決。

歐盟《網路韌性法案》

歐盟《網路韌性法案》（Cyber Resilience Act, CRA / EU 2024/2847）是歐盟針對具備數位元素產品（Products with Digital Elements, PDEs）所頒布的首個橫向強制性網路安全法規。

1. 核心規範原則

CRA 將資安責任直接歸屬於製造商、進口商與經銷商，主要原則包括：

  • 設計即安全（Secure-by-Design & Default）： 產品在規劃與開發階段即須納入網路安全考量，且預設設定需具備安全性。
  • 全生命週期管理： 製造商必須在產品生命週期內（至少 5 年或產品預期壽命期間）提供免費的資安更新與漏洞修補。
  • 軟體物料清單（SBOM）： 強制記錄與維護元件清單，確保供應鏈與第三方／開源套件的透明度與風險控制。
  • CE 標誌強制認證： 符合 CRA 要求的產品才可貼上 CE 標誌並於歐盟市場銷售。

2. 適用範圍與排除對象

適用範圍

涵蓋所有直接或間接連接至網路或裝置的硬體與軟體產品，例如：

  • 消費性電子： 智慧家電、網路攝影機、穿戴式裝置、路由器等。
  • 工業與商業設備： 工業控制器（PLC）、感測器、網關（IoT Gateway）及管理軟體。
  • 獨立軟體： 操作系統、韌體、應用軟體及各類聯網工具。

排除對象

已有其他專屬嚴格資安法規監管的產品不適用 CRA：

  • 醫療器材（受 MDR / IVDR 規範）
  • 車用設備（受 UN R155 / R156 等車用標準規範）
  • 民航航空設備與國防軍事產品

3. 產品風險等級與合格評鑑模式

CRA 依據產品的資安風險高低，將產品劃分為不同等級並採取不同的合格評鑑模式（Conformity Assessment）：

  1. 預設 / 一般產品（Default / Non-Critical）：
  • 評鑑方式： 製造商可透過自我宣告（Self-assessment）確認符合 CRA 技術要求並簽署 EU Declaration of Conformity。
  1. 重要產品 Class I（Important Class I）：
  • 評鑑方式： 若有完全套用歐盟「調和標準（Harmonised Standards）」，可採用自我宣告；若無，則需由歐盟認可之第三方合格評鑑機構（Notified Body）進行審查。
  1. 重要產品 Class II（Important Class II）與關鍵產品（Critical）：
  • 評鑑方式： 強制要求第三方驗證或取得指定之歐盟網路安全認證計畫（EUCC）證書。

4. 關鍵時間軸

時間 里程碑與法律義務
2024 年 12 月 10 日 CRA 法案正式生效（進入過渡期）。
2026 年 6 月 11 日 合格評鑑機構（Notified Body）相關要求生效。
2026 年 9 月 11 日 漏洞與資安事件通報義務強制上路（發生主動利用漏洞或重大事件時，須於 24 小時內通報 ENISA 與主管機關）。
2027 年 12 月 11 日 CRA 全面強制實施（不符合資安要求之產品不得在歐盟市場銷售）。

5. 罰則機制

若未遵守 CRA 規範，違規企業將面臨重罰：

  • 技術要求未合規： 最高 1,500 萬歐元 或 全球年營業額 2.5%（以較高者為準）。
  • 通報義務未履行： 最高 1,000 萬歐元 或 全球年營業額 2.0%（以較高者為準）。
  • 監管機關有權要求違規產品下架、召回或禁止在歐盟境內銷售。

6. 企業因應建議與現行參考標準

由於歐盟 CRA 的調和標準（Harmonised Standards）仍在由 CEN/CENELEC 與 ETSI 陸續制定與調和中，現階段企業可基於以下既有國際資安標準建置合規體系：

  • 工業控制與嵌入式設備： ISA/IEC 62443（特別是 62443-4-1 安全開發生命週期與 62443-4-2 元件安全）。
  • 消費性物聯網（IoT）： ETSI EN 303 645。
  • 軟體供應鏈與 SBOM： SPDX 或 CycloneDX 格式標準。
  • 通用資安驗證： ISO/IEC 27001、ISO/IEC 29147（漏洞揭露）及 ISO/IEC 30111（漏洞處理）。

如何判定我的數位產品在歐盟 CRA 下屬於一般類別、Class I 還是 Class II

判定數位產品在歐盟 CRA（Cyber Resilience Act）下的分類，關鍵在於「產品的核心功能」以及「產品若遭受破壞後可能造成的風險與連帶影響層面」。

歐盟 CRA 採用「負面清單法（Exclusion / Designated List）」：先檢查產品是否屬於 Annex III（重要產品 Class I / II） 或 Annex IV（關鍵產品）；若皆不在清單上，則預設歸類為一般類別（Default）。

您可以依照以下三步驟來進行判定：

第一步：是否落在 Annex III Class II（高風險重要產品）？

若產品具備極為關鍵的資安防護、系統底層控制或防篡改功能，通常屬於 Class II。此類產品強制必須由第三方機構（Notified Body）進行審查驗證。

常見 Class II 產品項目包括：

  • 底層虛擬化與容器系統： Hypervisors、Container runtime systems。
  • 資安防護設備： 防火牆（Firewalls）、入侵偵測與預防系統（IDS/IPS）。
  • 高安全性晶片與硬體： 具備防篡改能力的微處理器/微控制器（Tamper-resistant microprocessors / microcontrollers）。

💡 評鑑方式： 不可自我宣告，必須通過第三方認證（Modules B+C 或 Module H）。

第二步：是否落在 Annex III Class I（中風險重要產品）？

若產品具備身分驗證、加密、網路管理或保護關鍵隱私/安全等功能，但未達到 Class II 的底層影響力，則屬於 Class I。

常見 Class I 產品項目包括：

  • 資安與憑證工具： 密碼管理器（Password managers）、PKI 憑證核發軟體、VPN 軟體/設備、防毒/掃毒軟體。
  • 網路與系統管理： 網路管理系統、SIEM 系統、引導管理器（Boot managers）、作業系統（OS）、網路介面卡、路由器、數據機與交換器。
  • 安全相關晶片與組件： 具備資安相關功能的 MCU、MPU、ASIC 與 FPGA。
  • 特殊消費性/物聯網裝置：
  • 智慧家庭安全產品（如智慧門鎖、監控攝影機、嬰兒監視器、警報系統）。
  • 具備社交互動或定位追蹤功能的聯網玩具。
  • 具備健康監測功能或兒童專用的個人穿戴式裝置。

💡 評鑑方式： 若完全符合歐盟調和標準（Harmonised Standards），可採用自我宣告（Self-assessment）；若缺乏適用標準，則需經由第三方驗證。

第三步：是否不在清單內？（歸類為 Default 一般產品）

歐盟約有 80%～90% 的數位產品屬於此類別。只要產品不具備上述專用的高風險資安功能，且未列入 Annex III / IV，即屬於一般類別（Default）。

常見 Default 產品包括：

  • 一般消費性電子（如一般智慧家電、一般藍牙音響、智慧手錶/手環（非兒童用且無特殊健康數據監測））
  • 一般工業用非安全相關之感測器與資料擷取模組
  • 一般應用軟體（如文字處理軟體、圖像編輯軟體、相機 App 等）
  • 一般微控制器/單晶片（未宣稱具備硬體資安防護功能者）

💡 評鑑方式： 製造商直接進行**內部生產控制與自我宣告（Self-assessment）**並貼上 CE 標誌即可。

SBOM 說明

軟體物料清單（Software Bill of Materials，簡稱 SBOM），概念源自於製造業的「物料清單（BOM）」。

在實體製造中，BOM 會詳細記錄生產一台車或一部電腦需要哪些零件、螺絲與晶片；而在軟體開發中，SBOM 就是一份詳細記錄軟體產品中所有「軟體零件（Components）」與供應鏈關係的完整清單。

1. SBOM 裡面包含哪些內容？

根據美國國家電信暨資訊管理局（NTIA）定義的最低核心標準，一份標準的 SBOM 通常包含以下資訊：

  • 元件名稱（Supplier & Component Name）： 套件或套件庫名稱（例如 Log4j、React、cURL）。
  • 版本號（Version）： 該元件精確使用的版本（例如 2.14.1）。
  • 唯一識別碼（Identifiers）： 如 PURL（Package URL）或 CPE（Common Platform Enumeration），用於全球精確比對漏洞庫。
  • 依賴關係（Dependency Relationship）： 清楚標示「誰調用了誰」（包含直接引用與間接引用的第三方套件）。
  • 作者與簽署資訊（Author & Cryptographic Hash）： 確保 SBOM 檔案本身的真實性與防篡改。

2. 為什麼 SBOM 現在這麼重要？

現代軟體開發很少從零開始，約 80% 到 90% 的程式碼來自開源套件（Open Source Software）或第三方函式庫。這帶來了巨大的資安風險與合規挑戰：

① 快速定位與應對資安漏洞（Vulnerability Management）

當零日漏洞（Zero-Day Attack）爆發時（如 2021 年震驚全球的 Log4j 漏洞），沒有 SBOM 的企業需要花數週時間逐一檢查所有專案程式碼；而擁有 SBOM 的企業可以在幾秒鐘內透過自動化比對，精確定位公司旗下哪些系統使用了受影響的套件與版本。

② 防範軟體供應鏈攻擊（Software Supply Chain Attacks）

駭客常透過污染上游開源套件（如 SolarWinds 事件、npm 惡意套件）來入侵下游企業。SBOM 讓軟體供應鏈變得透明，企業能清楚掌握產品內到底裝了什麼。

③ 開源授權條款合規（License Compliance）

開源套件各有不同的授權條款（如 MIT、GPL、Apache 2.0）。SBOM 能協助法務與工程團隊盤點授權，避免因誤用具傳染性的授權（如 GPL）而面臨商業程式碼強制開源的法律風險。

④ 歐美法規強制要求（Legal & Regulatory Mandates）

  • 美國： 拜登政府簽署的第 14028 號行政命令，要求所有銷售給美國聯邦政府的軟體必須提供 SBOM。
  • 歐盟： 《網路韌性法案》（CRA）將 SBOM 列為產品進入歐盟市場的強制性合規要求之一。
