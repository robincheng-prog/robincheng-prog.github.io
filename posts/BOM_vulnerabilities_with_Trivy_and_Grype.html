如何使用 Trivy 與 Grype 對 CycloneDX SBOM 進行漏洞掃描

本指南接續〈如何手動補充與檢查 CycloneDX SBOM〉，說明如何在 Windows PowerShell 使用 Trivy 與 Grype 掃描 CycloneDX JSON SBOM，並比較兩套工具的結果。

重要：漏洞掃描結果會隨工具版本、漏洞資料庫時間及比對策略改變。報告應記錄掃描時間、工具版本及使用的 SBOM 檔名，方便後續追蹤。

一、掃描前準備

準備下列檔案：

  • 已完成補充並通過 CycloneDX Schema 驗證的 SBOM。
  • 與 SBOM 對應的正式 Release。
  • Trivy 或 Grype 的 Windows x64 官方執行檔。

二、下載 Trivy

Trivy 應從 Aqua Security 官方 GitHub Releases 下載：

  • 最新版本：https://github.com/aquasecurity/trivy/releases/latest/
  • 官方文件：https://trivy.dev/docs/latest/

本次初次測試使用 trivy_0.74.0_windows-64bit.zip；截至 2026 年 10 月 19 日，官方最新版本為 0.76.0。正式掃描前應再次查看 Releases，不要長期依賴本文件記載的版本號。

  1. 從官方 Releases 下載 Windows 64-bit 壓縮檔，例如 trivy_0.76.0_windows-64bit.zip。
  2. 將壓縮檔解壓縮到準備執行掃描的資料夾。
  3. 開啟 PowerShell，切換到解壓縮後的資料夾並確認工具可以執行：

三、使用 Trivy 掃描 SBOM

基本掃描

Trivy 會自動辨識 CycloneDX JSON。第一次執行通常會下載漏洞資料庫，因此需要網路連線並可能等待數分鐘。

儲存完整 JSON 報告

JSON 適合保存完整掃描證據及後續程式處理；終端機表格適合人工快速閱讀。

一般使用情境不需要另外操作漏洞資料庫；Trivy 會在需要時自動下載或更新。若終端機出現資料庫下載訊息，等待完成即可。

四、Trivy 結果判讀

主要欄位：

欄位 說明
Library SBOM 中被比對到的套件名稱
Vulnerability CVE 或其他漏洞識別碼
Severity 工具依資料來源判定的嚴重度
Installed Version SBOM 記錄的目前版本
Fixed Version 上游已知修正版本
Status 漏洞資料來源記錄的修正狀態

Status: fixed 表示上游已提供修正版，不表示目前安裝版本已完成修正。應比較 Installed Version 與 Fixed Version。

修正時仍應回到專案的直接／間接 NuGet 相依關係確認相容版本，完成升級、重新建置、測試、重建 SBOM，再重新掃描。

被跳過的元件

本次 Trivy 顯示下列 device-driver 類型不受該次 SBOM 掃描支援，因此被跳過：

  • JENSYS64 driver
  • WinIo64 driver
  • JENSYS32 driver
  • WinIo32 driver

被跳過不等於安全，也不等於沒有漏洞。這些項目應另外查核：

  • 原廠安全公告及 CVE。
  • 檔案版本、數位簽章與 SHA-256。
  • 驅動程式來源及是否仍受維護。
  • Windows Driver Blocklist、Microsoft 或硬體供應商公告。

Trivy 官方也提醒，以其他工具產生的 SBOM 作為輸入時，可能因缺少 Trivy 自訂 properties 而影響偵測準確度。因此應保留警告文字，不要只保存最後的漏洞數字。

五、下載 Grype

Grype 應從 Anchore 官方來源取得：

  • 最新版本：https://github.com/anchore/grype/releases/latest/
  • 官方安裝文件：https://oss.anchore.com/docs/installation/grype/

截至 2026 年 10 月 19 日，官方最新版本為 0.120.1。Windows 可下載 grype_0.120.1_windows_amd64.zip；實際使用時仍應重新確認最新版本。

  1. 從官方 Releases 下載 Windows AMD64 壓縮檔，例如 grype_0.120.1_windows_amd64.zip。
  2. 將壓縮檔解壓縮到準備執行掃描的資料夾。
  3. 開啟 PowerShell，切換到解壓縮後的資料夾並確認工具可以執行：

六、使用 Grype 掃描 SBOM

基本掃描

Grype 會由檔案內容自動辨識 SBOM 格式，第一次執行通常會下載漏洞資料庫，因此需要網路連線並可能等待數分鐘。

儲存 JSON 報告

一般使用情境不需要另外操作漏洞資料庫；Grype 會在需要時自動下載或更新。若希望終端機以 CVE 而不是 GHSA 為主，可在基本指令最後加上 --by-cve。

七、Grype 結果判讀

圖 2：Grype 0.120.1 掃描結果。兩筆漏洞的狀態皆為 fixed，代表上游已有修正版；畫面同時提供 EPSS 與 Risk 資訊。

Grype 的主要欄位包括目前版本（Installed）、修正版本（Fixed In）、漏洞識別碼、嚴重度、EPSS 與 Risk。fixed 同樣只代表已有修正版，不表示產品目前使用的版本已完成修正。

Grype 預設可能優先顯示 GHSA 識別碼；使用 --by-cve 可改以 CVE 顯示。JSON 報告中的 match type 也應納入判讀：exact-direct-match、exact-indirect-match 通常可信度較高，cpe-match 則應額外人工確認。

八、Trivy 與 Grype 比較

比較項目 Trivy Grype
維護組織 Aqua Security Anchore
CycloneDX SBOM 輸入 支援 JSON；使用 trivy sbom 支援 JSON/XML；使用 sbom: 或自動判斷
預設文字報告 Table Table
結構化報告 JSON、SARIF 等 JSON、SARIF、CycloneDX 等
CI 嚴重度門檻 --severity 搭配 --exit-code --fail-on
漏洞資料庫 Trivy DB，首次掃描通常自動下載 Grype DB，預設自動檢查更新
結果判讀特色 顯示 Installed／Fixed Version 與來源嚴重度 JSON 提供 match type；另提供 EPSS、risk 等排序資訊
第三方 SBOM 注意事項 官方明確警告可能因缺少自訂 properties 而降低準確度 依 SBOM 的 PURL、CPE、套件名稱及版本進行比對

兩套工具結果可能不同，常見原因包括：

  • 漏洞資料庫來源與更新時間不同。
  • 套件名稱、PURL、CPE 正規化方式不同。
  • 嚴重度採用的資料來源不同。
  • 直接比對、間接比對或 CPE 推測比對策略不同。
  • SBOM 缺少版本、PURL、CPE 或工具特定 properties。
  • 某些 CycloneDX component type 不在工具支援範圍。

不應只選擇漏洞數較少的工具。建議以兩者結果的聯集建立初步清單，再逐筆確認：

  1. CVE 是否確實對應 SBOM 中的元件與版本。
  2. 是直接相依或間接相依。
  3. 受影響程式碼是否存在於實際交付檔案。
  4. 產品是否會執行到受影響功能。
  5. 是否存在官方修正版或其他緩解措施。
  6. 兩套工具的資料來源、match type 與嚴重度依據。

Grype JSON 中的 exact-direct-match、exact-indirect-match 通常可信度較高；cpe-match 應額外人工確認。Trivy JSON 則可查看 SeveritySource 與各供應商嚴重度。

本次同一份 OpPredict SBOM 的實測比較

2026 年 10 月 19 日以 Trivy 0.74.0 與 Grype 0.120.1 掃描 OpPredict_sbom-v10_cyclonedx-1.6_20261019.json，兩套工具都找到相同的兩個漏洞：

元件與版本 CVE Trivy Grype
System.Text.Encodings.Web 4.7.1 CVE-2021-26701 Critical；列出不同版本分支的多個修正版本 Critical；Fixed In 4.7.2
System.Text.RegularExpressions 4.3.0 CVE-2019-0820 High；Fixed Version 4.3.1 High；Fixed In 4.3.1

Grype 預設報告可能優先顯示 GHSA 識別碼；加上 --by-cve 後可統一顯示上述 CVE。這兩筆在 Grype JSON 中都是 exact-direct-match。

此次兩套工具的漏洞數相同，表示這兩個 NuGet 套件的結果具有較好的交叉驗證；但不代表其他原生 DLL、EXE 或 driver 已被完整掃描。Trivy 明確警告跳過 4 個 device-driver，Grype 沒有顯示相同警告也不能推論它已完成驅動程式漏洞分析。缺少可比對版本或生態系識別碼的 generic 元件，兩套工具都可能無法從套件漏洞資料庫得到結果。

實測使用的 Grype DB 狀態為 valid、Schema v6.1.10，Built 時間為 2026-10-19T06:39:15Z。日後重新掃描時應記錄當次實際 DB 狀態，結果可能隨資料庫更新而改變。

十、發現漏洞後的處理流程

  1. 在專案檔及套件相依樹確認漏洞元件是直接或間接相依。
  2. 查閱套件供應商、安全公告及 CVE 官方資料。
  3. 選擇與產品相容的修正版，不要只依掃描器顯示的第一個版本升級。
  4. 重新建置並執行功能、相容性及回歸測試。
  5. 以新的正式 Release 重新計算 SHA-256。
  6. 重新產生及人工補充 SBOM，遞增 SBOM 文件版本並同步更新檔名。
  7. 使用最新漏洞資料庫重新執行 Trivy 與 Grype。
  8. 保存修正前後報告與處理紀錄。

若經分析確認漏洞不影響產品，可建立 VEX，記錄 not_affected 的理由與證據。不可直接刪除或忽略掃描結果而不留下決策紀錄。

十一、掃描紀錄與歸檔清單

每次正式掃描至少保存：

  • 本次使用的 SBOM 原始檔。
  • 對應的產品版本與 Release 識別資訊。
  • 掃描日期、時間與時區。
  • Trivy／Grype 版本。
  • 漏洞資料庫版本或更新時間。
  • 完整 JSON 報告，必要時另附 SARIF 或表格報告。
  • 工具警告、被跳過的元件及掃描限制。
  • 人工確認、修正、接受風險或 VEX 判定紀錄。
