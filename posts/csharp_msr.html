MagTek MSR (磁條讀卡機) 整合與 C# 開發實戰指南

本指南紀錄了在整合 MagTek 磁條讀卡機（如 Dynamag 系列）時的底層通訊原理、硬體加密機制，以及如何使用 C# 穩定接收並解析 POS HID 封包的完整實作。

1. 核心概念：POS HID vs. Keyboard 模式

MagTek 讀卡機通常有兩種運作模式：

  • Keyboard Emulation (鍵盤模擬)：隨插即用，將刷卡資料轉換為鍵盤敲擊動作（Keystrokes）。優點是簡單，缺點是若游標不在正確的視窗，資料會遺失或干擾操作。
  • POS HID (Vendor-Defined HID)：透過 USB 協定在背景傳輸封包。不會干擾滑鼠或鍵盤，必須透過 SDK 或 API 攔截資料。這是商業系統中最安全且最穩定的模式。

2. 硬體安全機制與常見踩坑 (RC=7)

開發者常嘗試發送 01 10 01 (Set Property) 試圖將 POS HID 切換為鍵盤模式，卻收到 RC=7 (MAC Error) 錯誤。

原因分析：
機器出廠時的安全等級 (Security Level) 設定。透過發送 00 15 (Get Property 15) 可以查詢狀態：

  • Level 2 (未加密)：允許軟體修改介面，刷卡資料為明文 ASCII。
  • Level 3/4 (已上鎖/硬體加密)：銀行或支付商已注入金鑰。硬體會直接阻擋所有修改介面或讀取明文的指令（回傳 RC=7）。

為什麼每次刷卡的密文都不一樣？(DUKPT 機制)

處於加密狀態的機器，採用 DUKPT (Derived Unique Key Per Transaction) 機制。每次刷卡後，硬體晶片會自動銷毀當前金鑰，並衍生出一把新金鑰。因此，即便連續刷同一張卡，封包內的 Encrypted Tracks 與 DUKPT Key Serial Number (KSN) 每次都會改變，這有效防止了重放攻擊 (Replay Attack)。

4. 關鍵防雷：解決視窗卡死與 StackOverflow

在開發 USB 背景監聽程式時，最常遇到關閉視窗時引發 Deadlock (死結) 或 StackOverflowException。這是因為 UI 執行緒與底層 ReadReport 的背景執行緒互相等待所導致。

標準解法：

  1. 建立 _isClosing 防禦旗標，避免系統重複呼叫關閉事件。
  2. 使用 Task.Run 將 CloseDevice() 丟到背景執行。
  3. 使用 Process.GetCurrentProcess().Kill() 強制中止殘留的監聽執行緒。

5. 測試與品管注意事項

若測試時發生讀取失敗 (FAIL)，請優先排除以下物理因素：

  1. 刷卡速度：過快或過慢皆會導致磁通量無法正常解析，需保持平穩中速。
  2. 卡片方向：確保磁條貼齊讀卡機底部的磁頭感應區。
  3. 卡片損耗：測試用的黃金樣卡 (Golden Sample) 若長期磨損消磁，會導致產線誤判設備異常。建議設定「三次刷卡皆失敗才判定為不良品」的容錯 SOP。
