如何手動補充與檢查 CycloneDX SBOM

本指南接續〈如何在 Visual Studio 2022 / 2026 / VS Code 上產生符合歐盟 CRA 規範的 SBOM〉。CycloneDX .NET CLI 能自動列出 NuGet 套件，但正式 Release 中的自研程式、原生 DLL、驅動程式、工具程式及部分授權資訊，通常仍需人工核對與補充。

重要：SBOM 的正確性比完整度分數重要。不可為了提高分數而猜測版本、授權、供應商或相依關係。CycloneDX BOM Studio 的 Completeness 是工具自身的品質提示，不代表已自動符合 CRA 的全部義務。

一、準備資料

人工補充前應準備：

  • CycloneDX .NET CLI 產生的原始 SBOM。
  • 實際交付客戶的正式 Release 資料夾。
  • Solution、專案檔、NuGet 套件及原始碼。
  • 第三方元件的官方網站、官方套件頁面、LICENSE 或授權條款。
  • 公司正式名稱、官方網址，以及經公司確認的共用聯絡信箱（如有）。

建議先保留工具產生的原始 SBOM，再以複本進行人工補充，以便追蹤差異。

二、以正式 Release 為核對基準

SBOM 應描述實際出貨內容，而不是只描述 Visual Studio 專案中的 NuGet 套件。

優先盤點 Release 資料夾中的下列檔案：

  • .exe：主程式、輔助工具、安裝或診斷程式。
  • .dll：.NET Assembly、原生 DLL、第三方 SDK。
  • .sys：Windows 驅動程式。
  • 其他會影響產品執行或安全性的韌體、模型及執行階段檔案。

不要把設定檔、紀錄檔或一般資料檔一律當成軟體元件；但應另外檢查 Release 是否意外包含密碼、Token、私鑰、服務帳號 JSON 或其他機密資料。

三、判斷哪些檔案需要成為元件

通常應加入 SBOM 的項目包括：

  • 產品主程式及公司自行開發的輔助程式。
  • 自研 DLL、原生 DLL 及驅動程式。
  • 隨產品交付且執行時會載入的第三方元件。
  • 雖未直接出現在專案參考中，但會由程式在執行時建立、解壓或載入的元件。
  • 執行產品所需的重要 Framework 或 Runtime，例如 .NET Framework 4.7.2。

常用 CycloneDX type：

檔案或元件 建議 type
主程式或獨立工具 EXE application
DLL、NuGet 套件 library
SYS 驅動程式 device-driver
.NET Framework 等執行框架 framework

四、元件欄位的證據優先順序

每個欄位都應保留可追溯的判定依據，建議順序如下：

  1. 正式 Release 檔案本身的版本資源與 SHA-256。
  2. NuGet 套件內的 .nuspec、LICENSE 或套件 metadata。
  3. 專案檔、原始碼、AssemblyInfo、Git tag 或正式建置紀錄。
  4. 原廠官方網站、官方文件或官方原始碼 repository。
  5. 公司內部經確認的元件資料。

搜尋引擎摘要、第三方下載站及檔案名稱本身不能單獨作為可信證據。

五、作者、製造商與供應商

這三個欄位的語意不同：

  • metadata.authors：建立 SBOM 的人員或組織聯絡資訊，可填 name、email、phone，不可直接填 URL。
  • metadata.manufacturer：建立產品或 BOM 的組織，可填公司名稱及網址。
  • metadata.component.supplier：向客戶提供主產品的組織，可填公司名稱、網址及聯絡資料。

十、使用 CycloneDX BOM Studio 檢查

  1. 開啟 https://cyclonedx.studio/。
  2. 匯入補充後的 JSON。
  3. 確認左下角顯示 Valid。
  4. 檢查 Dashboard 的 Components、Dependencies、Orphaned components 與 Circular dependencies。
  5. 查看 Completeness 分數及缺少項目。
  6. 修改本機檔案後必須重新匯入，瀏覽器不一定會自動讀取磁碟更新。

BOM Studio v0.9.2 的 12 項 Completeness 檢查

BOM Studio v0.9.2 每通過一項即增加約 8.33%，最後四捨五入：

  1. 已識別 supplier。
  2. 所有 components 都有 name。
  3. 所有 components 都有 version。
  4. 所有 components 都有 CPE、PURL 或 SWID 其中之一。
  5. 已記錄 dependencies。
  6. metadata 有 authors 或 manufacturer。
  7. metadata 有 timestamp。
  8. metadata 有 lifecycles。
  9. metadata 有建立工具資訊。
  10. 至少一個 component 有 hashes。
  11. 至少一個 component 有 licenses。
  12. 有 compositions 完整性聲明。

因此，通過 11/12 項會顯示 92%。如果某些二進位檔確實沒有版本資訊，維持 92% 比填入假版本取得 100% 更正確。

BOM Studio 版本更新後，計分邏輯可能改變。分數只能用於發現缺漏，不能取代 CycloneDX Schema 驗證、正式 Release 盤點、漏洞管理或 CRA 法規審查。

十一、建議的最終檢查清單

  • JSON 可正常解析，並通過 CycloneDX 1.6 Schema 驗證。
  • serialNumber 使用有效且固定的 UUID URN。
  • SBOM 的主產品名稱與版本符合正式 Release。
  • Release 中每個應納管的 EXE、DLL、SYS 都已處理。
  • SHA-256 來自正式交付檔案。
  • 沒有重複的 bom-ref。
  • dependencies 沒有引用不存在的 bom-ref。
  • 無孤立元件及不合理的循環相依。
  • 授權、供應商及版本都有可信證據；無法確認的資料沒有猜填。
  • 公司名稱、官方網址及聯絡方式使用經公司確認的資料。
  • Release 不包含密碼、Token、私鑰或不必要的服務帳號檔案。
  • SBOM 與對應 Release 一起保存，並保留產生工具、日期及人工修改紀錄。
