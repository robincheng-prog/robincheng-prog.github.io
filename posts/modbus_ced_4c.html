1.2 硬體對照測試

使用 C/C++ 開發的第三方串口除錯軟體，例如 Terminal v1.9b，進行相同的連線、斷線與重新連線測試：

  • CTS / DSR / CD 燈號皆正常。
  • COM Port 可以反覆開啟與關閉。
  • RS485 通訊功能正常。

RS485 硬體線路、電表及 CH340 硬體本身故障。

問題主要集中於 Python Serial 通訊方式與 Windows CH340 驅動之間的相容性。

2. 根因分析（Root Cause Analysis）

經過比對 Python 與原生 C/C++ 串口操作流程後，推測問題主要來自以下幾個層面。

2.1 pyserial 底層配置機制

Python 的 pyserial 在呼叫 open() 時，會進一步透過 Windows Serial API 對 COM Port 進行通訊參數配置。

其中包含：

  • SetCommState
  • DCB（Device Control Block）設定
  • DTR / RTS 狀態
  • 流量控制相關參數

部分參數在重新開啟 COM Port 時會被重新配置，可能觸發 CH340 Windows 驅動的相容性問題。

2.2 CH340 Windows 驅動相容性問題

在 Windows 環境下，CH340 驅動程式於處理特定 Serial DCB 重置與控制訊號設定時，可能產生異常狀態。

並導致 COM Port 無法再次正常開啟。

2.3 原生 C/C++ 與 Python 套件的操作差異

C/C++ 串口工具通常直接透過 Windows Win32 API 操作 Serial Handle，可以自行控制：

  • COM Port 開啟
  • Baud Rate
  • Data Bits
  • Stop Bits
  • Parity
  • Timeout
  • Buffer
  • DTR / RTS

因此，相較於 pyserial 的高階封裝，可以更精確地控制 Windows Serial API 的操作流程，避免不必要的 DCB 參數重置。

3.1 繞過高階套件，改用 Native Win32 C API

ReadFile 讀取 Serial Data

6. 總結與後續建議（Summary & Next Steps）

6.1 軟體面

當 Python 標準通訊套件，例如 pyserial，在特定 Windows Driver 環境下出現底層相容性問題時，可以考慮使用 Python ctypes 直接呼叫原生 Win32 API。

相較於引入額外的 C/C++ Library，此方式具有以下優點：

  • 不需要額外安裝第三方 C Library。
  • 可直接控制 Windows Serial API。
  • 可自行控制 DCB、Timeout、Buffer 等參數。
  • 可以降低高階 Serial Library 帶來的額外配置。
  • 更接近 C/C++ 原生串口程式的操作方式。

6.2 硬體面

若系統未來需要部署於長時間運作、工業現場或長期維運環境，建議優先選擇驅動與 Win32 Serial API 相容性較成熟的 USB-to-RS485 轉接方案。

例如：

  • FTDI FT232RL
  • Silicon Labs CP2102

相較於消費級 CH340 方案，這類晶片通常具有較成熟的 Windows 驅動支援，可降低 USB-to-RS485 轉接器造成的系統相容性風險。
