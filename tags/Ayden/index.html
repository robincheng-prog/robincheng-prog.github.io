軟體物料清單 (SBOM) 與漏洞掃描導入指南

作者： Ayden

一、 什麼是 SBOM？為什麼我們需要它？

SBOM（Software Bill of Materials） 是軟體的「成分標籤」，詳細記錄了專案中所使用的所有第三方套件、開源元件及版本號。

導入主因：

  1. 合規要求： 歐盟網路韌性法案 (CRA) 等國際法規強制要求產品出廠需具備 SBOM，並有對應的漏洞管理機制。
  2. 零日漏洞快速應變： 當爆發重大資安漏洞（如 Log4j 事件）時，透過掃描 SBOM，能在幾秒鐘內確認我們的產品是否受影響，無須重新編譯原始碼。

二、 團隊標準工作流程 (DevSecOps)

為了保持開發效率並兼顧資安，我們將採用「產出」與「掃描」分離的職責分工模式：

  • 開發團隊： 負責在編譯時，產出正確的 SBOM 檔案。
  • 資安/維運團隊： 拿著 SBOM 檔案進行漏洞比對。

分工優勢：

  • 掃描工具不需要取得原始碼，保護程式碼隱私。
  • 不綁定特定掃描工具，隨時可抽換 Grype、Trivy 或 Dependency-Track。

我們統一採用國際主流的 CycloneDX (JSON格式) 作為 SBOM 標準。

四、 資安端後續處理 (如何掃描漏洞)

拿到開發團隊提供的 sbom.json 後，後續可交由 CI/CD 或資安團隊透過以下工具進行漏洞比對：

  • Grype (推薦單機快掃)： 專為 SBOM 設計，速度極快。
    grype sbom:./sbom.json
  • Trivy： 廣泛使用的 DevSecOps 掃描器。
    trivy sbom ./sbom.json
  • OWASP Dependency-Track： 企業級漏洞管理平台。將 SBOM 上傳後，平台會每日自動比對最新 NVD 漏洞庫，爆發新漏洞時會自動告警，完全符合 CRA 法規要求。

問題主要集中於 Python Serial 通訊方式與 Windows CH340 驅動之間的相容性。

2. 根因分析（Root Cause Analysis）

經過比對 Python 與原生 C/C++ 串口操作流程後，推測問題主要來自以下幾個層面。

2.1 pyserial 底層配置機制

Python 的 pyserial 在呼叫 open() 時，會進一步透過 Windows Serial API 對 COM Port 進行通訊參數配置。

其中包含：

  • SetCommState
  • DCB（Device Control Block）設定
  • DTR / RTS 狀態
  • 流量控制相關參數

部分參數在重新開啟 COM Port 時會被重新配置，可能觸發 CH340 Windows 驅動的相容性問題。

2.2 CH340 Windows 驅動相容性問題

在 Windows 環境下，CH340 驅動程式於處理特定 Serial DCB 重置與控制訊號設定時，可能產生異常狀態。

可能造成：

並導致 COM Port 無法再次正常開啟。

2.3 原生 C/C++ 與 Python 套件的操作差異

C/C++ 串口工具通常直接透過 Windows Win32 API 操作 Serial Handle，可以自行控制：

  • COM Port 開啟
  • Baud Rate
  • Data Bits
  • Stop Bits
  • Parity
  • Timeout
  • Buffer
  • DTR / RTS

因此，相較於 pyserial 的高階封裝，可以更精確地控制 Windows Serial API 的操作流程，避免不必要的 DCB 參數重置。

3. 解決方案與架構轉型（Key Solutions & Architecture）

3.1 繞過高階套件，改用 Native Win32 C API

針對 Windows 平台，放棄使用 pyserial / pymodbus 直接控制 COM Port，改使用 Python 內建的 ctypes 模組，直接呼叫 Windows kernel32.dll 的原生 API。

SourceTree 基礎操作教學指南

作者： Ayden

本文件旨在幫助初學者快速上手 SourceTree 的介面與基本功能。SourceTree 是一款強大的 Git 圖形化介面工具，能讓你更直觀地管理程式碼版本。

1. 啟動與倉庫管理 (Repository Management)

在 SourceTree 的初始分頁中，你可以管理你的所有專案。

  • Local (本地): 顯示已存在於你電腦硬碟中的 Git 專案列表。
  • Remote (遠端): 連結 GitHub/GitLab 帳號後，可直接查看雲端上的專案。
  • Clone (複製): 將雲端倉庫（如 GitHub 網址）下載到本地電腦。
  • Add (加入): 將電腦中現有的 Git 資料夾掛載到 SourceTree 列表中。
  • Create (建立): 在指定的資料夾初始化一個全新的 Git 倉庫。

2. 環境設定與 SSH 配置 (Options & SSH)

為了確保能順利提交代碼並與遠端伺服器連線，請確認以下設定：

Tools > Options

  • 使用者資訊 (Default user information):
    • Full Name: 設定你在 Commit 紀錄中顯示的名字。
    • Email Address: 必須與你的 Git 平台（如 GitHub）帳號信箱一致。
  • SSH 客戶端設定: 建議使用 OpenSSH 並正確指向你的私鑰路徑。

3. 遠端倉庫與金鑰指定 (Remote Settings)

當您需要將專案推送到雲端時，必須設定遠端連結路徑，並指定正確的身份驗證金鑰。

Settins > Remotes

  • Remote name: 預設通常為 origin，這是遠端倉庫的代號。
  • URL / Path: 填寫雲端倉庫的位址。
    • 進階技巧: 如果您有多組 SSH Key，可以在路徑前面使用別名（例如 keyB-deploy:帳號/倉庫.git），這能強制 SourceTree 使用您在 config 檔中定義的特定金鑰與該倉庫通訊。
  • Remote Account: 連結特定的主機帳號（如 GitHub），以便進行更深層的整合操作。

4. 工作區介面解析 (File Status View)

當你開啟一個專案後，最常用的就是「File Status」視圖，這裡處理「現在」的改動。

核心區域說明：

  • 左側導覽列: 切換「檔案狀態」、「歷史紀錄」、「分支管理」。
  • 已暫存區 (Staged files): 準備要打包提交的檔案。
  • 未暫存區 (Unstaged files): 電腦中已被修改但尚未打包的檔案。
  • 比對區 (Diff View): 點擊檔案可看具體改動（紅色代表刪除，綠色代表新增）。

5. 頂部工具列詳解 (Action Toolbar)

這是你對 Git 下指令的「動作按鈕區」，也是最核心的控制中心：

  • Commit (提交): 將已暫存 (Staged) 的檔案「打包」並加上訊息備註，存入你電腦的本地紀錄中。
  • Pull (拉取) / Push (推送): * Pull: 從雲端伺服器下載最新的進度到你的電腦。
    • Push: 把你電腦裡的最新紀錄上傳到雲端伺服器分享給他人。
  • Fetch (擷取): 檢查雲端有沒有新東西，但先不自動合併，讓你先掌握遠端動態。
  • Branch (分支) / Merge (合併): * Branch: 建立「平行時空」或開外線來開發新功能，不影響主線。
    • Merge: 將不同分支的開發成果合併在一起。
  • Stash (暫存): 臨時的隱藏區。如果你程式寫到一半必須去處理緊急 Bug，可以用 Stash 將目前改動暫時「藏」起來。
  • Discard (放棄修改): 點擊後會把你選取的檔案改動全部抹除，還原到最後一次存檔的狀態。
  • Tag (標籤): 為特定的 Commit 加上標籤（如 v1.0），方便日後快速回溯。

6. 歷史紀錄與版本溯源 (History View)

「History」視圖讓你查看專案的「過去」。

  • 分支圖 (Graph): 以線條顯示分支的開叉與合併過程。
  • 標籤指示: main 代表本地位置，origin/main 代表雲端位置。

7. 快速操作工作流

  1. 修改: 在編輯器改完存檔。
  2. 暫存: 在 Unstaged files 點擊 + 移至 Staged files。
  3. 提交: 點擊 Commit 並輸入訊息。
  4. 同步: 點擊 Push 上傳至雲端。

本教學由 SourceTree 介面截圖整理而成，適合 Git 入門使用者參考。
