Nuvoton M2354 BSP 軟體物料清單 (SBOM) 生成說明

作者: Kenny Tsai

1. 概述

隨著全球對軟體供應鏈安全的要求日益提高（歐盟網路韌性法案 CRA），提供精確的軟體物料清單 (SBOM) 已成為硬體製造商與韌體開發者的標準要求。

說明如何為 Nuvoton M2354 系列微控制器（支援 Arm TrustZone 技術）的支援包 (BSP) 生成符合 CycloneDX v1.6 規範的 JSON 格式 SBOM，以實現自動化資安漏洞追蹤與授權合規管理。

2. 環境與核心工具準備

要自動化生成 M2354 的 SBOM，您需要準備以下開源 SCA（軟體組成分析）與驗證工具：

  1. Anchore Syft：用於掃描原始碼目錄並生成 SBOM 結構。
    • 安裝 (Linux/macOS): curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh | sh -s -- -b /usr/local/bin
    • 安裝 (Windows): winget install anchore.syft
  2. CycloneDX CLI：用於驗證生成的 JSON 是否符合國際規範。
    • 下載: 從 CycloneDX 官方 GitHub Releases 獲取對應作業系統的執行檔。
  3. Python 3.8+：用於執行後處理腳本，注入硬體特有屬性與靜態庫雜湊值。

3. 範疇隔離策略 (Scope Policy)

在嵌入式系統開發中，BSP 往往包含了大量測試程式碼、說明文件與範例專案。若將這些檔案一併納入 SBOM，會導致資安掃描時產生大量誤報 (False Positives)。

因此，首要步驟是定義產品範疇 (Product Scope)：

  • 納入 (include_path)：最終會被編譯、連結至實際韌體的函式庫（如 Library/CMSIS、Library/StdDriver）。
  • 排除 (exclude_path)：不進入生產環境的檔案（如 SampleCode/、Document/）。

4. SBOM 生成步驟實作

步驟一：使用 Syft 執行初始掃描

在定義好範疇後，我們使用 Syft 掃描 Library/ 資料夾，並指定輸出格式為 CycloneDX JSON。

步驟二：後處理 (Post-Processing) 注入 BSP 客製化屬性

嵌入式系統有其特殊的授權與預編譯二進位檔（例如 SmartcardLib 中的 .a 檔）。我們需要透過腳本（通常是 Nuvoton 內部工具或客製化 Python 腳本）將以下屬性注入到基礎 SBOM 中：

  1. 特定授權宣告：將 SmartcardLib 等專有元件標記為 Nuvoton Proprietary。
  2. 屬性擴充 (Properties)：加入 bsp:sbom-category、bsp:component-origin: first-party 等屬性。
  3. 靜態庫雜湊防護 (SHA-256)：掃描閉源靜態庫的雜湊值，確保防篡改。例如：
    • bsp:static-lib:0:path: Library/SmartcardLib/libsmartcard.a
    • bsp:static-lib:0:sha256: c426c4b9402edb3a8147bcb8ce9f7dbc48a22707eefac4be8d3ce734ec9232e3

註：執行後處理腳本後，產出的最終檔案即為 m2354bsp_Product_SBOM_cdx.json。

步驟三：規範驗證

確保生成的 SBOM 符合 CycloneDX v1.6 標準，避免上傳至管理平台時解析失敗。

5. 後續資安與合規應用

產出 m2354bsp_Product_SBOM_cdx.json 後，可以將其應用於以下場景：

  1. 開源授權審計 (License Compliance)
    交由法務或合規團隊檢查，確保產品未誤用具傳染性條款的 GPL 授權，並檢視 Nuvoton Proprietary 與 Apache-2.0 的分發合規性。
  2. 提供產品認證
    將 SBOM 隨同編譯好的 .bin 或 .hex 韌體以便滿足其安全稽核要求。

2.2 風險矩陣與緩解措施 (Risk Matrix & Mitigations)

3. 安全架構與設計規範 (Security Architecture & Design)

3.1 信任根與硬體安全 (Hardware Root of Trust)

  • 安全啟動 (Secure Boot)： 建立開機鏈信任根，防止非授權韌體執行。
  • 密鑰安全儲存： 私鑰與敏感憑證儲存於 [ TPM 2.0 / HSM / Secure Element / eFuse ] 中。

3.2 存取控制與身份驗證 (Security-by-Default)

  • 無硬編碼密碼： 嚴禁預設密碼 (No Hardcoded Passwords)。
  • 首次開機安全： 強制要求使用者首次啟動時更換密碼，或使用單一設備獨立預設密碼 (Unique Default Password)。
  • 權限控管： 採用角色存取控制 (RBAC) 與最小權限原則 (Least Privilege)。

3.3 介面硬化 (Interface Hardening)

  • 實體埠關閉： 量產版本預設停用或焊接封鎖 Debug UART / JTAG 介面。
  • 服務最小化： 關閉未使用的網路服務與埠號 (如 Telnet, HTTP 80 埠)。

4. 安全開發生命週期 (Secure SDLC Process)

4.1 原始碼安全規範

  • 靜態檢測 (SAST)： 於 CI/CD Pipeline 整合 [ SonarQube / Fortify / Checkmarx ]，告警標準設定為 Zero Critical Vulnerability。
  • 動態檢測 (DAST) / 模糊測試 (Fuzzing)： 定期執行 API 及 protocol 模糊測試。

4.2 機密資訊管理 (Secrets Management)

  • 代碼庫管理： 使用 [ GitGuardian / Trufflehog ] 掃描原始碼，禁止提交 API Key 或 Private Key。
  • 運行期密鑰管理： 使用 [ HashiCorp Vault / AWS KMS / 環境變數 ] 動態注入。

4.3 第三方套件稽核

  • 開源管理流程： 引進第三方 Lib 前進行授權與已知 CVE 漏洞檢測。

5. 軟體物料清單管理 (SBOM & Supply Chain Security)

1.1 SBOM 格式與產出機制

  • 自動化生成工具： 整合於 CI/CD 流程中 (使用 [ Syft / Trivy / Black Duck ])。
  • 匯出格式： [ CycloneDX JSON / SPDX JSON ] 機器可讀格式。

1.2 SBOM 核心欄位涵蓋

  • 元件名稱 (Component Name)
  • 版本號 (Version)
  • 供應商/作者 (Supplier)
  • 唯一識別碼 (PURL / CPE)
  • 授權條款 (License)
  • 依賴關係圖譜 (Dependency Graph)

1.3 CVE 自動化動態掃描

  • 比對頻率： 每日/每週將 SBOM 與 NVD / OSV 資料庫進行比對。
  • 漏洞通報機制： 發現 High/Critical CVE 時自動触發 Jira/Slack 告警。

6. 漏洞管理與協調披露策略 (Vulnerability Handling & CVD)

6.1 漏洞披露政策 (CVD Policy)

  • 資安聯繫管道： security@[company_domain].com
  • security.txt 設置： 於 https://[company_domain]/.well-known/security.txt 部署法規標準檔。
  • PSIRT 團隊職責： 專責接收、驗證、分析與回應外部資安通報。

6.2 漏洞修補 SLA (Patch Management)

  • 緊急漏洞 (Critical/High CVE)： [ X ] 天內釋出修補檔/臨時緩解方案。
  • 中低風險漏洞 (Medium/Low CVE)： 併入下一次定期版本更新 ([ Y ] 天內)。

7. 安全更新與事件通報機制 (Secure Update & Incident Response)

7.1 安全更新機制 (OTA / FOTA)

  • 傳輸與簽章防護： 升級包使用 ECC-256 簽章，並透過 TLS 加密傳輸。
  • 防呆與降級保護： 支援雙 Bank (A/B) 備份刷寫及防降級機制 (Rollback Protection)。
  • 安全維護承諾期： 本產品承諾提供至少 [ 5 ] 年（至 YYYY-MM-DD）免費安全修補更新。

7.2 歐盟事件通報 SOP (EU CRA Reporting)

當發現被主動利用的零日漏洞或重大資安事件時，觸發以下程序：

  • 24 小時內 (早期預警)： 通報 ENISA 與國家級 CSIRT，說明事件影響範圍。
  • 72 小時內 (事件通知)： 提交初步風險評估報告與緩解措施。
  • 1 個月內 (最終報告)： 提交根本原因分析 (RCA) 與終極修補方案。

8. 測試驗證與合規聲明 (Testing, Verification & DoC)

8.1 測試報告摘要

  • 滲透測試 (Penetration Test)： 由 [ 第三方資安公司 / 內部獨立測試小組 ] 於 YYYY-MM-DD 完成，修補複測全數通過。
  • 自動化掃描報告： SAST、SCA 掃描通過證明附於 [ 附錄 B ]。

8.2 歐盟符合性聲明 (EU DoC 草案)

  • 聲明內文： 本公司特此聲明，上述產品完全符合歐盟《網路韌性法案》(EU Cyber Resilience Act) 附件一及附件七之規定。
  • 標誌授權： 於產品本體/包裝標註 CE 標誌。

附錄：實務自我查核清單 (CRA Compliance Checklist)

  • SBOM 是否為機器可讀格式？ (CycloneDX / SPDX JSON，非 PDF)
  • 是否已設定 security.txt？ (符合 CVD 通報規範)
  • 是否具備防降級與數位簽章的 OTA 更新機制？
  • 產品包裝/官網是否明確標示安全更新終止年份？ (至少 5 年)
  • 內部是否已建立 24h / 72h 歐盟通報 SOP？
  • 若有 ISO 27001 / IEC 62443-4-1 認證，相關程序書是否已連結引用？
